Automata in the Real World

Everything in this course is running somewhere right now: in your editor’s syntax highlighter, your compiler, your network stack, the chip in your phone. This chapter connects each theoretical idea to the systems built on it.

Intuition — why lexers and parsers are separate

Tokens are regular, so they can be recognized by a DFA in one pass with no stack — extremely fast. Only the nested structure needs the (more expensive) parser. Splitting the work along the Chomsky hierarchy is both a performance and a design decision. The lexer typically uses longest match (keep running the DFA, remember the last accepting position) plus a priority order to break ties between, say, the keyword if and the identifier rule.

LL vs. LR in one paragraph

An LL parser builds the tree top-down: its stack holds what it still expects to see — exactly the CFG→PDA construction from Chapter 9 — and it chooses which rule to expand by peeking at $k$ upcoming tokens. It cannot handle left recursion ($E \to E + T$). An LR parser builds bottom-up: it shifts tokens onto the stack and reduces right-hand sides to variables when it recognizes a handle. Remarkably, the set of viable stack contents is a regular language, so LR parsers use a DFA (the “LR automaton”) to decide when to reduce — a finite automaton steering a pushdown automaton.

Regex engines

  • Backtracking engines (Perl, PCRE, Python, Java, JavaScript, .NET): try alternatives depth-first. Support backreferences and lookaround, but can take exponential time. ^(a+)+$ on aaaaaaaaaaaaaaaaaaaaaaaa! explores ~$2^{n}$ ways to split the a’s before failing. This is ReDoS, and it has taken down production systems (a single regex caused a global Cloudflare outage in 2019).
  • Automaton engines (RE2, Go regexp, Rust regex, grep’s DFA mode, Hyperscan): Thompson NFA simulated with state sets, with DFA states built lazily and cached. Guaranteed $O(|R| \cdot |w|)$ time. They refuse backreferences because those are not regular.
Pitfall — “You can’t parse HTML with regex”

Arbitrarily nested tags form a context-free (not regular) language — the pumping lemma says a true regex cannot match <div>n … </div>n. Regexes are fine for flat patterns inside HTML; for structure, use a parser.

State machines in software design

Finite-state machines are a design tool, not just theory. Whenever an object has modes and events move it between them — a TCP connection (LISTEN, SYN-SENT, ESTABLISHED, FIN-WAIT…), a checkout flow, a media player, a game character’s AI, an elevator controller — modelling it explicitly as an FSM eliminates whole classes of bugs (“what happens if pause arrives while loading?”). The transition table forces you to answer every (state, event) pair. Libraries such as XState, Spring State Machine and Boost.MSM, and statecharts (Harel, 1987: hierarchical, concurrent FSMs, now part of UML) build on this.

// The DFA design discipline, applied to a UI
state: Idle | Loading | Success | Error
on FETCH:   Idle → Loading, Error → Loading
on RESOLVE: Loading → Success
on REJECT:  Loading → Error
// every other (state, event) pair: explicitly ignored — no impossible states

Hardware

Every synchronous digital circuit is a finite-state machine: flip-flops hold the state, combinational logic computes $\delta$ and the outputs. Hardware engineers design controllers explicitly as Moore or Mealy machines (Chapter 7), and minimization and state encoding (binary, one-hot, Gray code) directly affect chip area and power. CPU instruction decoders, bus protocols, USB and PCIe link layers, and cache-coherence protocols are FSMs.

Verification and model checking

To prove a system never deadlocks or always eventually responds, model it as a (huge) finite automaton and check it against a temporal-logic specification. The key ideas:

  • Büchi automata accept infinite strings (an accepting state must be visited infinitely often) — the right model for reactive systems that never terminate.
  • An LTL formula like “every request is eventually granted” is translated into a Büchi automaton for its negation; the product with the system model is checked for emptiness (cycle detection). Product + emptiness — the same tools as Chapter 6.
  • Tools: SPIN, NuSMV, TLA+ (used at Amazon, Microsoft and elsewhere to verify distributed protocols), CBMC. Turing Award 2007: Clarke, Emerson, Sifakis.

Undecidability is why this works only for finite (or finitely abstracted) models — and why bounded model checking and SAT/SMT solvers (NP-hard problems, solved well in practice) are so central.

Text, search and data

  • String matching: KMP is a DFA for a single pattern; Aho–Corasick builds one automaton for thousands of patterns at once (used in antivirus scanners, intrusion detection like Snort, and grep -F).
  • Search indexes: Lucene stores its term dictionary as a minimal finite-state transducer (FST) and runs fuzzy search with Levenshtein automata — DFAs that accept every string within edit distance $k$ of a word.
  • Spell checking, morphology, speech: weighted finite-state transducers (OpenFst) compose dictionaries, pronunciation rules and language models.
  • Data formats: JSON, XML and most file formats are defined by CFGs; validators for JSON Schema and XML Schema use tree automata.

Biology and linguistics

  • Hidden Markov models — probabilistic finite automata — find genes and align protein families (HMMER, Pfam).
  • Stochastic CFGs model RNA secondary structure: base pairs nest like parentheses (Infernal, Rfam).
  • Natural language: Chomsky invented the hierarchy to study human language; whether natural languages are context-free was debated for decades (Swiss German cross-serial dependencies show they are not quite). Modern NLP still uses CFG parsing, and large language models are studied through the lens of formal language recognition.

The limits, in practice

  • Undecidability: no perfect bug finder, termination checker, malware detector or dead-code eliminator exists (Rice). Real tools choose to be sound (no missed bugs, some false alarms — e.g. type systems) or complete (no false alarms, some missed bugs — e.g. testing, fuzzing).
  • Turing completeness everywhere: C++ templates, the TypeScript type system, SQL with recursive CTEs, CSS+HTML with user interaction, Excel formulas, Minecraft redstone, Magic: The Gathering. A consequence: type-checking TypeScript can, in principle, fail to terminate — which is why compilers impose recursion limits.
  • NP-hardness: scheduling, register allocation, package dependency resolution (installing packages with version constraints is NP-complete), circuit layout. Industry relies on SAT/SMT/ILP solvers and heuristics.
  • Configuration languages: designers increasingly choose deliberately non-Turing-complete languages (Dhall, CUE, Starlark’s restricted form, eBPF’s verifier-checked programs) so that evaluation always terminates and can be analysed — the principle of least power from Chapter 14.

Exercises

Write a regex for decimal numbers like -12, 3.14, 6.02e23, 1E-9 (as a lexer would). Is the language regular? easy

-?(0|[1-9][0-9]*)(\.[0-9]+)?([eE][+-]?[0-9]+)?. Yes — it uses only union, concatenation and star (character classes and ? are shorthand).

Explain why (a|a)*b is dangerous for a backtracking engine on input aaaa…a (no b) but harmless for RE2. medium

Each a can be matched by either alternative, so a backtracking engine explores $2^n$ paths before concluding there is no b. RE2 tracks the set of NFA states, which stays tiny (both alternatives lead to the same states), so it runs in linear time.

Model a traffic light with a pedestrian button as a Mealy machine (states, inputs, outputs). medium

One possible design: states Green, GreenRequested, Yellow, Red; inputs tick, button; outputs the light colour. Green –button→ GreenRequested; GreenRequested –tick→ Yellow; Yellow –tick→ Red (output: walk signal on); Red –tick→ Green. On button in other states, stay. Every (state, input) pair is defined — the discipline that prevents bugs.

Your team wants a tool that flags every function that might never return, with no false alarms. What do you tell them? easy

Impossible in general (Halting Problem / Rice). They must give up one requirement: flag all possibly-non-terminating functions with some false alarms (sound), or flag only definitely-non-terminating ones and miss some (no false alarms), or restrict the language (e.g. only structurally recursive loops).

Takeaways
  • Lexers = regex → NFA → DFA; parsers = CFG → PDA (LL top-down, LR bottom-up with a DFA inside).
  • Automaton regex engines are linear; backtracking engines risk ReDoS.
  • FSMs are a design discipline for software and the literal structure of hardware.
  • Model checking = product automaton + emptiness, on Büchi automata for infinite behaviours.
  • Undecidability and NP-hardness shape real tools: approximations, solvers, and deliberately limited languages.
